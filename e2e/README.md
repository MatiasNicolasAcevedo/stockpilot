# Runner E2E

T-003 A materializa stack/runner; B agrega recorridos reales de sesión/fallos; C los conecta al gate FULL (`bash scripts/verify.sh`, `--e2e`) y al job CI `e2e`. En modo producto `e2e.sh` exige Node ≥ 24 en el host antes de construir y ejecuta `harness/test_sanitize.py` en la imagen exacta antes de la matriz. `bash scripts/e2e.sh --harness` acredita únicamente arranque real de Chromium/SPA compilada y readiness API/proveedor. `bash scripts/e2e.sh` ejecuta `npm test`: matriz auth/system en ambos proyectos Chromium y, desde T-003 D2, `swagger.spec.ts` solo en desktop (el proyecto móvil lo excluye por `testIgnore`), con la documentación encendida por el overlay E2E según ADR 0003. Ningún harness sustituye esos recorridos.

Compose combina base/auth/overlay E2E, env-file ficticio explícito y proyecto validado `stockpilot-e2e-<único>`. Rechaza recursos preexistentes y retira solo su red/volúmenes/contenedores, incluidos detenidos. Sin puertos host. Chromium comparte el namespace de red de nginx; `http://localhost` coincide en browser/proxy/backend/callback. Issuer `http://host.docker.internal:8090/default` idéntico en todo el flujo, resuelto por alias al proveedor. Sin hosts globales.

Imagen y paquete Playwright fijados a 1.64.0; `npm ci` instala durante build. No descarga dependencias durante escenarios. `init` evita zombies; `shm_size: 1gb` conserva IPC propio sin compartir el del host. Browser no monta socket Docker.

Config: `forbidOnly`, cero retries, un worker, contextos nuevos por test, Chromium 1280/375 px. Timeout de casos con lifecycle 90 s; fixture reconstruida por caso con deadline 180 s, control 120 s/readiness HTTP 60 s. No hay sleeps de escenario: assertions web-first/poll con deadline; la observación de expiración verifica durante 3 s que solo hubo un me 401 y ninguna navegación. No hay MSW ni route/fulfill ni API exitosa fabricada. Cancelación inicia el flujo con HTTP real y el cookie jar compartido del contexto (redirects detenidos), comprueba authorize real del proveedor y usa el state emitido por el backend en el callback de error; el code exitoso del proveedor se descarta. Login/callback exitoso sí se recorre por navegación/teclado.

El host ejecuta `scripts/run-e2e.mjs` con la lista exacta de archivos/perfiles Compose autorizados; buzón atómico de archivos en artifacts/control, operaciones cerradas sobre server/oidc/DB del proyecto propio. Browser sin Docker socket, puertos nuevos ni endpoint productivo de control. UUID/claims ficticios únicos por caso; el proveedor y backend se reinician al preparar cada fixture, preservando la DB propia. Cada caso restaura backend/readiness en finally. Un worker y ausencia de fullyParallel serializan caídas/reinicios, sin dependencia del orden. La consulta SQL acota issuer/subject y devuelve solo id/createdAt, permitiendo comprobar una fila exacta y estabilidad. 403 comercial conserva `OidcLoginIT`/`SecurityConfigTest` y componentes `AuthSession.test.tsx`; no se añade recurso comercial.

Retiene trace/screenshot en fallo y reportes HTML/JUnit. `e2e/artifacts/<proyecto>` es local/ignorado; los artefactos brutos contienen diagnósticos sensibles y no se publican. Sin storageState ni identidades reales. Reporter de consola imprime solo títulos/estados, omitiendo errores que podrían incluir URLs auth. `harness/sanitize.py` exporta automáticamente en `sanitized/` un HTML/JUnit mínimo con el estado de fallo conservado, timeline de trace por allowlist (sin parámetros/resultados/errores originales, red, cookies, DOM, fuentes ni recursos) y PNG solo de pantallas SPA conocidas con manifest del fixture. El trace saneado es una cronología de acciones: el replay/diagnóstico completo permanece solo en el original local. Revisar los exports antes de compartir; nunca subir en bloque el directorio bruto, control, logs auth ni archivos del proveedor.

Ensayo rojo dirigido: `STOCKPILOT_E2E_ASSERT_FAILURE=1 bash scripts/e2e.sh` selecciona system.spec.ts en ambos viewports y cambia únicamente el texto esperado por el assert final de recuperación real de system/info. Debe fallar ambos, exportar trace/screenshot/HTML/JUnit conservando fallos y limpiar recursos. Sin esa variable vuelve la matriz completa y su aceptación normal; no se debilita ningún assert. `STOCKPILOT_E2E_ASSERT_FAILURE=swagger bash scripts/e2e.sh` hace lo mismo con `swagger.spec.ts` (un caso desktop): solo cambia el dato esperado en el resultado de «Try it out» de system/info, después de observar la respuesta real 200. Las pantallas de Swagger no están en la allowlist de capturas, así que su export conserva el fallo y la cronología sin imágenes. El export es fail-closed: se arma en `sanitized.partial/`, se audita y recién entonces se publica como `sanitized/`; un export rechazado o interrumpido no deja nada compartible (la CI sube solo `sanitized/`). `harness/test_sanitize.py` prueba con canarios sintéticos el descarte de cookies/URL/query/errores/resultados/DOM/red/fuentes y de capturas sin manifest, conservando el failure JUnit.

`bash scripts/test-e2e-lifecycle.sh` delega al Docker real; adaptador exclusivo de test inyecta server exit42 en startup, detiene backend antes de readiness, envía TERM y reporta error de cleanup después de retirar recursos. Exige la evidencia de cada causa inyectada (`server-1 exited (42)` vía `entrypoint` del overlay, deadline de readiness, error de cleanup), señal 143, cero recursos propios, segunda ejecución y rechazo del proyecto ordinario; un nonzero por otro motivo no pasa (C corrigió el overlay de arranque, que antes no inyectaba el fallo). `--verify-only` ensaya `verify.sh --e2e`: fallo de arranque real → `e2e FALLÓ (exit 1)` y TERM durante up → exit 143 tras el cleanup de e2e.sh. Runner rojo usa `scripts/e2e.sh --runner-failure`: ejecuta un contenedor real con `node -e 'process.exit(42)'` y exige exit42 exacto, sin depender de ausencia de tests ni de interceptar docker.exe desde Node en Windows. `--runner-only` repite solo ese caso y las guardias. No acredita producto. Mantener intactos los Bash durante cada ensayo en ejecución (TR de A).
