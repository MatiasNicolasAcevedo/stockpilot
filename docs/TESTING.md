## Gate local: `scripts/verify.sh`
Se ejecuta con Bash (Git Bash/WSL) desde la raíz y despacha contenedores con Compose. Cualquier fallo devuelve exit code distinto de cero y un resumen por suite.

| Comando | Qué ejecuta |
|---|---|
| `bash scripts/verify.sh` | Todas las suites de la fase actual (FULL: docs, server, client, e2e). Único gate de entrega; requiere Docker y Node ≥ 24 en el host para el control de la suite E2E |
| `bash scripts/verify.sh --docs` | docs-check en `node:24.21.0-alpine` (servicio `docs-check`) |
| `bash scripts/verify.sh --server` | Runner `server-tests`: `./mvnw -B -ntp clean verify` |
| `bash scripts/verify.sh --client` | Runner `client-tests` (imagen `verify` de `client/Dockerfile`, reconstruida con `--build`): `npm run verify` = `typecheck` (`tsc -b`, incluye tests) → `lint` (cero warnings) → `format:check` → `test:ci` (Vitest + cobertura v8) → `build` |
| `bash scripts/verify.sh --e2e` | `scripts/e2e.sh` en modo producto: proyecto Compose único/propio, prueba del saneador en la imagen exacta, matriz B (5 casos × desktop 1280/móvil 375) más el smoke Swagger (1 caso, solo desktop por configuración), retries 0, export saneado solo si su auditoría pasa y cleanup propio. Falla antes de construir si el host no tiene Node ≥ 24 |
| `bash scripts/verify.sh --fast` | Fase actual sin E2E; solo iteración. El resumen la declara parcial: nunca habilita ready, revisión ni merge (igual que `--docs/--server/--client/--e2e` sueltos; `--docs` vale como gate solo si `--policy` informa DOCS_ONLY) |
| `bash scripts/verify.sh --policy <base>` | Muestra la política (DOCS_ONLY o la fase) del diff contra `<base>`, sin ejecutar suites |

**Señales y cleanup.** Cada suite corre como hijo directo (`exec`) en segundo plano. INT/TERM/HUP reenvían TERM a la suite en curso (los hijos en segundo plano de un shell no interactivo heredan SIGINT ignorado), `verify.sh` espera a que termine su limpieza, no inicia las siguientes y sale 130/143/129 con el resumen `INTERRUMPIDA`/`NO EJECUTADA`. `e2e.sh` retira solo su proyecto aunque la señal llegue durante build/up/tests. Ensayo: `bash scripts/test-e2e-lifecycle.sh --verify-only` (fallo de arranque real → `e2e FALLÓ (exit 1)`/exit 1; TERM durante up → exit 143; ambos con cero recursos propios).

**Backend en contenedor (default) y alternativa preaprobada.** `server-tests` monta `./server`, una caché Maven (`stockpilot_m2-cache`) y el socket de Docker, con `TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal`; Testcontainers crea PostgreSQL hermanos. Comprobado en Docker Desktop/Windows el 2026-10-12. Si en otra máquina no funcionara tras dos configuraciones documentadas (por ejemplo socket montado y override de host), `STOCKPILOT_SERVER_TESTS=host` ejecuta `./mvnw -B -ntp clean verify` en el host con JDK 21 contra el mismo Docker Desktop: mismas suites, Testcontainers, imagen, formato y JaCoCo; `verify.sh` informa qué variante usó. Aplicarla exige registrar motivo en esta sección, en las trampas de SETUP y un ADR breve. Hoy **no** está aplicada.

## Políticas de verificación en CI (`verify-required`)
El workflow [`ci.yml`](../.github/workflows/ci.yml) corre en `pull_request` hacia `main` (`opened`, `synchronize`, `reopened`, `ready_for_review`) y en `push` a `main`, con `concurrency` que cancela ejecuciones reemplazadas. El job agregado **`verify-required` siempre se emite** e informa política, base y HEAD.

| Política | Cuándo | Exige |
|---|---|---|
| `DRAFT` | PR en draft | Corre clasificador (con sus pruebas), docs-check, backend rápido (`spotless:check test`), client completo y E2E real (confirma el HEAD publicado); `verify-required` **falla a propósito** aunque todo esté verde, para que un verde nunca provenga de la pasada reducida |
| `DOCS_ONLY` | Cada entrada del diff es un archivo regular agregado/modificado de la allowlist | docs-check verde; server, client y e2e `skipped` (no aplicables). Cualquier suite técnica ejecutada, pendiente o ausente rechaza |
| `FULL` (fase) | Cualquier otro diff, rutas desconocidas, renombres/borrados, modos no regulares, diff vacío o error del clasificador | docs, server (`clean verify`), client y e2e `success` |

**Allowlist DOCS_ONLY** (`scripts/ci/classify-diff.mjs`, desde T-003 C): Markdown de raíz, `docs/**/*.md`, `AGENTS.md`/`CLAUDE.md` de raíz/`server`/`client` y `LICENSE`, solo con estado A/M y modo de archivo regular (`100644`). Son técnicos: Markdown bajo código (`server/src/x.md`, `client/src/x.md`, `e2e/README.md`, `server/README.md`), archivos no Markdown bajo docs (`docs/x.mjs`, ejemplos/imágenes), extensiones no exactas (`.MD`), workflows, scripts, configuración, dependencias, migraciones, ejemplos de entorno, rutas desconocidas, renombres, borrados, symlinks/gitlinks/ejecutables y errores. Lee `git diff --raw -z` sobre `base...head` (sin rutas entrecomilladas). El rojo previo de la allowlist anterior (`*.md`, `docs/**`) y la matriz completa están en `scripts/ci/classify-diff.test.mjs`. Modificar el clasificador, el agregado o sus pruebas exige el gate técnico. `plantilla/` no forma parte del repo ni del diff.

**Agregado** (`scripts/ci/verify-required.mjs`, matriz en `verify-required.test.mjs`): exige fase `FULL` y clasificador `success`; `DRAFT` rechaza siempre aunque las suites estén verdes; draft desconocido rechaza. `FULL` exige docs/server/client/e2e `success`; `DOCS_ONLY` exige docs `success` y server/client/e2e `skipped`. Ausente, `pending`, `skipped` (en FULL), `cancelled`, `failure` o política desconocida (incluida `BOOTSTRAP`) rechazan. Siempre escribe el resumen del job. El nombre del check requerido y el ruleset no cambian.

**Cierre de M0 y ampliaciones fundacionales: siempre FULL**, también cuando el último commit es documental. La CI clasifica todo el PR (`base...head` contra la base), así que un HEAD documental final después de commits técnicos sigue en `FULL` (caso probado); el gate local `bash scripts/verify.sh` ejecuta FULL sin mirar el diff. `--fast` y las suites sueltas no habilitan revisión ni merge.

**Job `e2e`**: paralelo a server/client tras `classify`, se omite solo en DOCS_ONLY; `timeout-minutes` 45 (paso 40), Node del host para el control cerrado y `bash scripts/verify.sh --e2e` con proyecto `stockpilot-e2e-ci-<run>-<intento>`. En fallo sube únicamente `e2e/artifacts/<proyecto>/sanitized/`, que el saneador publica solo tras auditar (fail-closed); retención 7 días, `if-no-files-found: ignore`. Brutos, `control/`, logs auth y archivos del proveedor nunca se suben.

Eficiencia de la capa gratuita: jobs en paralelo con `timeout-minutes`, caché Maven/npm de `actions/setup-*`, acciones fijadas por SHA, artefactos solo en fallos con retención de 7 días, sin workflows programados ni ejecuciones duplicadas por push de rama. La CI confirma; no se usa para depurar a prueba y error.

## Reglas
Prueba dirigida de R1 (T-001): con el stack local healthy, `node scripts/test-proxy-outage.mjs` usa Node del host sin dependencias npm.
